This file has two parts. The top part, down to the line "Generated part", is written by hand. ## What the drill is

16 scripted disasters (`drill/DISASTERS.md`) were each played in 4 setups, 3 times: 192 runs, plus a negative control of 6 runs, {{records_total}} records in all. The list, the predictions and the rules (`drill/PREREG.md`) were fixed before the first scored run (PREREG.md:3, :106). Their sha256 are the ones the run logs recorded (see the checks at the end).

| Arm | Setup (PREREG.md section 1) |
|---|---|
| 1 | Nothing. Muse Code as it comes, no hooks. |
| 2 | A diligent git user: `git add -A && git commit --allow-empty` before every turn, plus `muse rewind` (conversation only). |
| 3 | The engine hand-wired into Muse's settings with no adapter: only the hook event names are matched. |
| 4 | The adapter plus the engine. |

Arm 4 is held against arms 1 and 2 ("does it save the work when things go wrong") and against arm 3 ("what did the event work add").

{{replay_count}} disasters ({{replay_ids}}) ran in replay mode, batch `scored-1`. The harness builds Muse-shaped hook payloads, runs each arm's real hooks and runs the scripted commands itself. It starts no Muse and calls no model (`drill/harness/README.md:31`). D15 needs a real model and a real `/compact`, so it ran live, batch `d15-live-1` (section "D15 ran live"). Every cell in the generated part is labelled replay or live.

Limits stated in PREREG.md before the runs (section 9, line 102): the data is synthetic, the calls are scripted, the disaster list was written by an AI agent, and the drill does not measure false alarms, speed or cost. PREREG.md:42 also asks for a second replay under the other deny contract (`strict`), published beside the headline as a sensitivity run. That run is not in this result.

## Why arm 3 missed on D11 and D12

Predicted: D11 arm 3 {{d11_pred}}, D12 arm 3 {{d12_pred}}. Measured: NR in {{a3_nr}} runs. In {{a3_undo_none}} runs the recovery step `torpor undo 1` exited 0 and printed "Turn 1 changed no files, so there is nothing to undo." (`recovery.steps` in `drill/results/scored-1/runs.jsonl`).

The cause is in the code. Engine 2.3.1 matches Claude Code's tool names. Its list of file-editing tools is `EDIT_TOOLS = ["Edit", "Write", "MultiEdit", "NotebookEdit"]` (engine `src/hook.rs:20` and `src/capture.rs:24`), and it takes a shell call to be one with `tool == "Bash"` (`src/hook.rs:835`). The version is `Cargo.toml:3`, 2.3.1. These are lines of the engine repository at commit 495ce08, the build commit named in `engine.lock`. That repository is not part of this one, so `results.mjs` does not check them. They were checked by hand when this file was written, with `git show 495ce08:src/hook.rs` and the like. Muse Code sends `bash`, `edit_file` and `write_file` (`drill/DISASTERS.md:37`). Without the adapter the names do not match, so the engine records no per-turn change, and `torpor undo 1` finds nothing.

This is why the adapter exists. `src/hook/normalise.rs:9-11` renames `bash` to `Bash`, `edit_file` to `Edit` and `write_file` to `Write`. With the adapter (arm 4) the same two disasters end {{d11_a4}} (D11) and {{d12_a4}} (D12).

PREREG.md:116 flagged this risk before the scored run: the real engine in arm 3 had answered `torpor undo 1` with "nothing to undo" on a harness test, "so the arm 3 predictions of D11 and D12 may be wrong; they stay frozen, and a miss is published as a miss". The predictions were not changed.

## D07: the one loss against the better of arms 1 and 2

D07 is a database in use. Cells: {{d07_row}}. The loss was predicted in advance: "Red cell: yes, a database in use" (`drill/DISASTERS.md:259`) and `Predicted: {{d07_pred}}` (`drill/DISASTERS.md:275`), with "arm 4 is predicted to lose to arm 2" (`drill/DISASTERS.md:280`).

Arm 2 saves it. The three database files are untracked and not ignored (`drill/DISASTERS.md:260`), so the git auto-commit before the turn holds all three, and `git reset --hard` returns them byte for byte (`drill/DISASTERS.md:278`). The record agrees: oracle line `{{d07_oracle2}}` (RESTORED-EXACT means the folder after recovery equals the folder before the disaster, `drill/oracles/files.mjs:13`). In arms 3 and 4 the three files stay lost: `{{d07_oracle3}}` (arm 3), `{{d07_oracle4}}` (arm 4). The reason was written in advance: a database in use, meaning its `-wal` file is not empty, is not saved, even though `rm` gets its own save point (`drill/DISASTERS.md:279` and `:280`). The records show both. In arm 4, `torpor back --with-data --id 2` printed `{{d07_said4}}` and then `{{d07_busy}}` The `torpor back` of arm 3 printed the same last line. ## D15 ran live

D15 was added after scored-1, because replay cannot play it: scored-1 recorded NOT-RUN for all {{records_dropped}} D15 runs (the generated part lists them). This departs from PREREG.md section 3 ("chosen once, before the first scored run", line 40). It is written down in `drill/results/d15-live-1/run-log.md:9` and in `method.json` as `batch_label`: "{{d15_label}}". The records show these times: scored-1's run log was created at {{scored_created}}, the D15 runs lasted {{d15_window}}. The run log adds that the batch came "before its tally was read", and that the list, script, oracle and predictions were unchanged (`run-log.md:9`). In this section every `run-log.md` is `drill/results/d15-live-1/run-log.md`.

Result: {{d15_ps}} runs ended PS ({{d15_per_arm}} in arms 1 to 4). Muse's own compaction summary kept the code word every time, so D15 shows no difference between the four setups:

- PREREG.md:58 calls a run informative only when the compaction summary lacked the code word. Muse's own summary held it in {{d15_summary}} runs (`summaryHasNonce` true), and the first prompt stayed in the part of the conversation Muse keeps after `/compact` in {{d15_tail}} (`nonceInTail` true). So {{d15_informative}} runs are informative (the rule is `drill/DISASTERS.md:520`).
- So D15 is a red cell that was not expected: arm 4 ties the better of arms 1 and 2, because all four arms passed. The D15 prediction was `{{d15_pred}}` for arms 1 to 4. Arms 1, 2 and 3 were predicted FL and ended PS, so those three predictions missed. D15 adds {{d15_adds}}.
- Arm 4's pass did not come from the engine. Its note held the rule with the code word masked as `[hidden]` (`run-log.md:51`; `engineContext` false in {{d15_a4_engctx}} arm 4 runs). The engine masks any run of 16 or more letters, digits and `_+=-` that holds a letter and a digit (engine `src/mask.rs:53-68`), and the code word of {{d15_a4_masked}} arm 4 runs has that form (the `nonce` field of the records). `drill/DISASTERS.md:526` lists this, marked NV (not verified), among the conditions of the arm 4 prediction: the stored copy of the sentence "not being redacted". The tap files that show the note are in the per-run folders, which are kept locally.
- The code word was also in a file outside the project in {{d15_outside}} runs: Muse's own session index (`{{d15_outside_files}}`, `run-log.md:51`). The pre-registered oracle (`oracles/memory.mjs`) checks the project folder only, so the outcome is PS. PREREG.md:58 says "the code word in no file". Read strictly, the {{strict_n}} runs would be INVALID and D15 would have no valid run. The generated checks give that case: the four tallies would be {{strict_same}}. Both readings are given. The published outcome is PS.

Limits of these records (`run-log.md:59`): the `header` of its `run-log.json` was filled by a helper script, not by the harness; `adapter.git_head` differs from scored-1's while the adapter binary has the same sha256; the setting that switches off web tools is not verified (traffic went to `api.meta.ai:443` only).

## The tally fix

Before this change `tally.mjs` printed "?" for the tap row count of a live run in its list of excluded runs. A live record keeps its tap in a side file and holds only the count per event (`tap_events`). It now reads the row count the same way for both kinds (`tapRows` in `drill/harness/tally.mjs`): the length of the inline tap for a replay record, the sum of `tap_events` for a live record. The prediction misses also take their reason from the caller instead of "to be written". This changes what is printed and nothing else. The cell, rank and tally rules of PREREG.md section 7 are unchanged, and the checks at the end show that the new code makes scored-1's own `tally.md` again, byte for byte. `drill/harness/selftest.mjs` has cases with a live row.

## What is published

`drill/results/scored-1/` and `drill/results/d15-live-1/` hold copies of `runs.jsonl` (the records), `run-log.json` and `tally.md`, and for d15-live-1 also `run-log.md` and `method.json`. `drill/harness/publish.mjs` made them. It replaces absolute paths with `$ROOT` (the project folder), `$HOME` (a run's sandbox home folder, and the home folder of the machine) and `$TMP` (a run folder, or the temp folder), and changes nothing else. `drill/results/SOURCES.json` holds the sha256 of each raw file that was read and of each copy. The per-run folders (`runs/` of both batches, `calibration/` of d15-live-1: Muse session files, work trees, tap files) are not published. They are kept locally.
