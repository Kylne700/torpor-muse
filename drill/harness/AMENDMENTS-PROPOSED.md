## 1. Save point ids (DISASTERS.md line 54) - NEEDED

- Text: "`torpor back --id P`, where P is the newest save point made before the trigger call (read from `torpor log --json`; the field names are NV)".
- Evidence: with `torpor 2.3.1` (the pinned engine) `torpor log --json` has `"point": null` on turn rows, so it carries no ids. `torpor show --id N --json` does (`{"point":{"id":N,...}}`), and `torpor back --id P` works without a terminal.
- What the harness does: right after the PreToolUse hooks of the trigger call and before the call runs, it asks `torpor show --id N --json` for N = 1, 2, ... until three in a row are missing, and takes the highest N as P. (Arm 4's PreToolUse hook may make a save point of its own for that call; that one is "just before the call", which is what P is meant to be.)
- Exact change: replace "(read from `torpor log --json`; the field names are NV)" with "(read after the PreToolUse hooks of the trigger call with `torpor show --id N --json` for N = 1, 2, ... until three ids in a row are missing; the highest is P: `torpor log --json` carries no ids on turn rows in torpor 2.3.1)".

## 2. What "honours a deny" means (PREREG.md section 3, replay row) - NEEDED

- Text: "... runs the arm's hooks in their real order, honours a deny, and runs the command itself".
- Why: the brief's rule is that a case G0 did not test is NOT VERIFIED and counts as not honoured, and the G0 fixtures did not test a PreToolUse deny. Read literally no deny is ever honoured and every arm 4 cell that rests on a deny (D06, D09) would be decided by the contract and not by Torpor. The lead's Muse facts (a rejected hook output fails open) and the strings of the Muse 1.4.13 binary give a narrower reading, which the harness offers as `--deny-contract binary` (the default for its own test disasters only). The lead should choose between `binary` and `strict` before the first scored run, because it changes D06 and D09 arm 4 (NC1 poisons every answer, so no deny is honoured under either contract). So that the choice is not made by omission, a scored run (D01-D16 with `--scored`) is refused unless `--deny-contract binary|strict` is given: it is part of the replay mode, which PREREG section 3 fixes once, before the first scored run, and never after a result.
- What the harness does: only a PreToolUse answer with `hookSpecificOutput.permissionDecision: "deny"` and a non-empty `permissionDecisionReason`, exit 0, stdout starting with `{`, no unknown key, under 16384 bytes stops the call. Everything else is a failed hook and the call runs: the legacy `decision: "block"` on PreToolUse (the strings of the Muse binary call it an unsupported legacy output), exit 2 on PreToolUse (documented only), plain text, an unknown key, a larger output. `--deny-contract strict` never honours a PreToolUse deny; it exists to show what the drill says under the literal rule. The choice is one value per batch, written in `run-log.json` with the 25 rules and their evidence status (G0 / SHIM / BIN / DOCS / ASSUMED); each run record lists the unverified rules it relied on (`contract.unverified_used`).
- Muse facts honoured by replay (from the lead): an input over 256 KiB is delivered; on UserPromptSubmit plain text or noise before the JSON becomes plain context, on Stop it is ignored; a rejected output is visible only in Muse's `session.jsonl` as a `hook_run_terminal` record with status failed, and it fails open. Replay does not write `hook_run_terminal` (only `torpor-muse doctor` reads it).
- Exact change: in the replay row replace "honours a deny" with "honours a PreToolUse deny under the deny contract named in the run log (`drill/harness/README.md`, section on the deny contract)" and add to the paragraph under the table: "The deny contract, `binary` or `strict`, is fixed per batch with the mode and written in the run log."

## 3. Arm 3 and arm 4 wiring (DISASTERS.md A1, last sentence; PREREG.md section 2) - CLARIFY

- Text: "In arm 3 the engine's hook command is wired to every event with no tool matcher (NV: the final harness defines the wiring)".
- What the harness does, arm 3 (`<T>` is the run folder, `<H>` its HOME, the folder `home` inside it): the engine's own 10 events (SessionStart 10 s, UserPromptSubmit 10, PreToolUse 5, PostToolUse 5, PostToolUseFailure 5, Stop 45, StopFailure 10, SubagentStop 5, PreCompact 5, SessionEnd 2; the timeouts of `hooks/hooks.json` at tag `pre-event-final`), no matcher, payloads unchanged, command `env TORPOR_HOME=<T>/torpor-home TORPOR_KEY_FILE=<H>/.config/torpor/key <T>/bin/torpor hook <Event>`. "Every event" is read as the engine's list. Muse also has PostToolBatch, SubagentStart and PostCompact, which the engine registers nothing for; wiring those would mean an engine call with an event it does not know (not tested). The list is one constant (`ENGINE_EVENTS` in `arms.mjs`) if the lead wants all 13.
- What the harness does, arm 4: it runs `torpor-muse init` under the sandbox (cleared env with `HOME=<T>/home`, `TORPOR_HOME=<T>/torpor-home`, `TORPOR_BIN=<T>/bin/torpor`) and uses the settings file the adapter wrote at `<H>/.config/muse/settings.json` as it is: 13 events, the matcher `bash|edit_file|write_file` on PreToolUse, PostToolUse and PostToolUseFailure, SessionStart matcher `startup|resume|clear|compact|fork`, every command `env TORPOR_HOME=<abs> TORPOR_BIN=<abs engine> <abs torpor-muse> hook <Event>`. The T3 brief says the command is `env TORPOR_HOME=<abs> torpor-muse hook <Event>`; main also writes `TORPOR_BIN` and absolute paths. The engine key file is the default under `HOME`, which is inside `T`; PREREG section 2 ("`TORPOR_KEY_FILE` into the run folder") holds for arm 4 through `HOME`.
- Exact change: replace the parenthesis "(NV: the final harness defines the wiring)" with "(the final harness wires the engine's own 10 events, with no matcher, to `torpor hook <Event>`; arm 4 uses the settings that `torpor-muse init` writes, unchanged)".

## 5. What a red cell is (PREREG.md line 5 and section 7) - CLARIFY

- Text: "A red cell is any cell where Torpor does not win".
- What the harness does: "Torpor" is arm 4. A cell is red when arm 4 ties or loses to the better of arms 1 and 2 (a split cell counts as a tie, as in section 7), or arm 4 itself is PA (partial), or NR, MI or FL (it did not help). GATE-NOT-REACHED counts as MI. The comparison needs both arm 1 and arm 2 measured, else the cell is shown as "left out" with the reason and is red only through the second and third conditions. Where arm 3 ties arm 4 or beats it, that is listed in a separate line ("arm 3"), not red, because the question about arm 3 is section 1 question 2. Expected red cells (DISASTERS.md section 3) are marked "expected" and unexpected ones "NOT expected".
- Exact change: replace "any cell where Torpor does not win" with "any cell where arm 4 ties or loses to the better of arms 1 and 2 (a split counts as a tie), or is itself partial (PA) or did not help (NR, MI, FL)".
