# Disaster drill: results

This file has two parts. The top part, down to the line "Generated part", is written by hand. Each number in it is filled in by `node drill/harness/results.mjs` from the published records, and that command stops if a fact stated here no longer matches the records or a cited line. The rest is generated by the same command. `node drill/harness/results.mjs --check` tells whether this file is what the records make.

## What the drill is

16 scripted disasters (`drill/DISASTERS.md`) were each played in 4 setups, 3 times: 192 runs, plus a negative control of 6 runs, 198 records in all. The rules (`drill/PREREG.md`) were written before any run (PREREG.md:3). Before the first scored run the list, the predictions, the recovery steps and the rules could be amended, each time with a dated log entry saying "no scored run has happened" (PREREG.md:106). The log has two entries: v2 of 2026-10-26 (PREREG.md:112) and v3 of 2026-10-27 (PREREG.md:117). After the first scored run nothing in the list or the predictions may change (PREREG.md:107). The sha256 of `PREREG.md` is the one both run logs recorded, and that of `DISASTERS.md` the one the scored-1 run log recorded (see the checks at the end).

| Arm | Setup (PREREG.md section 1) |
|---|---|
| 1 | Nothing. Muse Code as it comes, no hooks. |
| 2 | A diligent git user: `git add -A && git commit --allow-empty` before every turn, plus `muse rewind` (conversation only). |
| 3 | The engine hand-wired into Muse's settings with no adapter: only the hook event names are matched. |
| 4 | The adapter plus the engine. |

Arm 4 is held against arms 1 and 2 ("does it save the work when things go wrong") and against arm 3 ("what did the event work add").

15 disasters (D01, D02, D03, D04, D05, D06, D07, D08, D09, D10, D11, D12, D13, D14, D16) ran in replay mode, batch `scored-1`. The harness builds Muse-shaped hook payloads, runs each arm's real hooks and runs the scripted commands itself. It starts no Muse and calls no model (`drill/harness/README.md:31`). D15 needs a real model and a real `/compact`, so it ran live, batch `d15-live-1` (section "D15 ran live"). Every cell in the generated part is labelled replay or live.

Limits stated in PREREG.md before the runs (section 9, line 102): the data is synthetic, the calls are scripted, the disaster list was written by an AI agent, and the drill does not measure false alarms, speed or cost. PREREG.md:42 also asks for a second replay under the other deny contract (`strict`), published beside the headline as a sensitivity run. That run is not in this result.

## Why arm 3 missed on D11 and D12

Predicted: D11 arm 3 EX, D12 arm 3 PA. Measured: NR in 6 of 6 runs. In 6 of 6 runs the recovery step `torpor undo 1` exited 0 and printed "Turn 1 changed no files, so there is nothing to undo." (`recovery.steps` in `drill/results/scored-1/runs.jsonl`).

The cause is in the code. Engine 2.3.1 matches Claude Code's tool names. Its list of file-editing tools is `EDIT_TOOLS = ["Edit", "Write", "MultiEdit", "NotebookEdit"]` (engine `src/hook.rs:20` and `src/capture.rs:24`), and it takes a shell call to be one with `tool == "Bash"` (`src/hook.rs:835`). The version is `Cargo.toml:3`, 2.3.1. These are lines of the engine repository at commit 495ce08, the build commit named in `engine.lock`. That repository is not part of this one, so `results.mjs` does not check them. They were checked by hand when this file was written, with `git show 495ce08:src/hook.rs` and the like. Muse Code sends `bash`, `edit_file` and `write_file` (`drill/DISASTERS.md:37`). Without the adapter the names do not match, so the engine records no per-turn change, and `torpor undo 1` finds nothing.

This is why the adapter exists. `src/hook/normalise.rs:9-11` renames `bash` to `Bash`, `edit_file` to `Edit` and `write_file` to `Write`. With the adapter (arm 4) the same two disasters end EX (EX EX EX) (D11) and PA (PA PA PA) (D12).

PREREG.md:116 (amendment v2 of 2026-10-26, whose entry says "No scored run has happened", PREREG.md:112) flagged this risk before the scored run: the real engine in arm 3 had answered `torpor undo 1` with "nothing to undo" on a harness test, "so the arm 3 predictions of D11 and D12 may be wrong; they stay frozen, and a miss is published as a miss". The predictions were not changed.

## D07: the one loss against the better of arms 1 and 2

D07 is a database in use. Cells: arm 1 NR (NR NR NR), arm 2 EX (EX EX EX), arm 3 NR (NR NR NR), arm 4 NR (NR NR NR). The loss was predicted in advance: "Red cell: yes, a database in use" (`drill/DISASTERS.md:259`) and `Predicted: NR | EX | NR | NR` (`drill/DISASTERS.md:275`), with "arm 4 is predicted to lose to arm 2" (`drill/DISASTERS.md:280`).

Arm 2 saves it. The three database files are untracked and not ignored (`drill/DISASTERS.md:260`), so the git auto-commit before the turn holds all three, and `git reset --hard` returns them byte for byte (`drill/DISASTERS.md:278`). The record agrees: oracle line `RESTORED-EXACT no-loss=no lost=0 critical-intact=yes` (RESTORED-EXACT means the folder after recovery equals the folder before the disaster, `drill/oracles/files.mjs:13`). In arms 3 and 4 the three files stay lost: `NOT-RESTORED no-loss=no lost=3 critical-intact=no` (arm 3), `NOT-RESTORED no-loss=no lost=3 critical-intact=no` (arm 4). The reason was written in advance: a database in use, meaning its `-wal` file is not empty, is not saved, even though `rm` gets its own save point (`drill/DISASTERS.md:279` and `:280`). The records show both. In arm 4, `torpor back --with-data --id 2` printed `Going back to save point 2 (before rm -f data/app.db data/app.db-wal data/app.db-shm, today 03:50).` and then `Not touched: data/app.db (nothing to bring back, its database was busy).` The `torpor back` of arm 3 printed the same last line. The red-cell list below marks D07 "loses to the better of arms 1 and 2, arm 4 did not help" (expected in `DISASTERS.md`).

## The tally fix

Before this change `tally.mjs` printed "?" for the tap row count of a live run in its list of excluded runs. A live record keeps its tap in a side file and holds only the count per event (`tap_events`). It now reads the row count the same way for both kinds (`tapRows` in `drill/harness/tally.mjs`): the length of the inline tap for a replay record, the sum of `tap_events` for a live record. The prediction misses also take their reason from the caller instead of "to be written". This changes what is printed and nothing else. The cell, rank and tally rules of PREREG.md section 7 are unchanged, and the checks at the end show that the new code makes scored-1's own `tally.md` again, byte for byte. `drill/harness/selftest.mjs` has cases with a live row.

## What is published

`drill/results/scored-1/` and `drill/results/d15-live-1/` hold copies of `runs.jsonl` (the records), `run-log.json` and `tally.md`, and for d15-live-1 also `run-log.md` and `method.json`. `drill/harness/publish.mjs` made them. It replaces absolute paths with `$ROOT` (the project folder), `$HOME` (a run's sandbox home folder, and the home folder of the machine) and `$TMP` (a run folder, or the temp folder), and changes nothing else. `drill/results/SOURCES.json` holds the sha256 of each raw file that was read and of each copy. The per-run folders (`runs/` of both batches, `calibration/` of d15-live-1: Muse session files, work trees, tap files) are not published. They are kept locally.

## How to re-run

- `node drill/harness/results.mjs --check` tells whether this file is what the published records make; `node drill/harness/results.mjs` writes it.
- `node drill/harness/tally.mjs drill/results/scored-1` and `node drill/harness/tally.mjs drill/results/d15-live-1` make the tally of one batch; the `tally.md` files next to the records were made like that.
- `node drill/harness/publish.mjs --root DIR --tmp DIR --home DIR --out drill/results RAW_SCORED_DIR RAW_LIVE_DIR` makes the copies from the raw batch folders, which are only on the machine that ran the drill. `--root` is the project folder the batches ran in, `--tmp` the temp base their runs used, `--home` the home folder of that machine; the values are not published, because they are the paths that are replaced. Compare the sha256 in `drill/results/SOURCES.json` with those of the raw files.
- Self-tests: `node drill/harness/selftest.mjs`, `node drill/oracles/selftest.mjs`, `sh drill/workspaces/selftest.sh`.
